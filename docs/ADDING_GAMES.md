# Adding a game

## 1. Define the mechanic and deterministic inputs
Choose a stable lowercase route ID. Start with HTML/CSS/SVG; introduce a canvas engine only when it earns its weight. Decide what makes a puzzle valid, how play ends, and what must be saved to resume it.

Use a pure generate(seed) function in src/lib/games/<id>/engine.ts. A generator can have game-specific configuration, but every generation-affecting value must be included in its identity/share link. All current games use standard configuration. Fivefold, Kings, and Ribbon use generator v1; Catdog and Word Ladder default to v2 and retain v1 for published links and saves. Extend validation before exposing another configuration or version, and never silently reuse an incompatible puzzle's save key.

Daily seed encoding is JSON.stringify(['daily', gameId, calendarDate, 'standard', generatorVersion]), supplied by dailyIdentity. Resolve today's calendar date using `localDate()` from the browser's local clock and timezone. Preserve the original encoding for each published version; v1 daily seeds still end in 1. Use seedIdentity for arbitrary-seed mode, which passes the exact URL-decoded string, including an empty string, without trimming, case folding, or Unicode normalization. These namespaces need not produce distinct boards; seeds can collide in any finite puzzle space.

Use an explicitly defined integer hash/seeded PRNG. Freeze its algorithm, seed encoding, data ordering, and content dependencies. Add a few fixed seed vectors to catch accidental mapping changes. If a generator needs search, use deterministic traversal and work bounds, not timeouts that choose different boards on different devices. Prefer constructing legal puzzles. A Web Worker is warranted when measured generation blocks interaction; import it only from the active game's module and terminate it on disposal.

Measure structural variety, not just the number of seeds: compare king/solution arrangements and region geometry after normalizing color labels, rotations, and reflections. Label shuffles alone do not create new geometry, and fixed color-to-row/column assignments can reveal answers. A constructed legal solution proves solvability, not uniqueness or difficulty; judge completion against the rules rather than only that stored solution. Time generation separately from expensive validation/canonicalization, and report device/runtime, sample size, and tail latency before adding a worker.

For copyrighted data, record the exact source/revision and preserve its required license notice. Never fetch a dictionary or puzzle feed at runtime. Dictionaries belong inside the lazy game dependency graph.

## 2. Build the component
Create src/lib/games/<id>/<Game>.svelte. Receive identity: PuzzleIdentity. Keep generated data, input, scoring, and completion state local to this component. The route keys it by puzzleKey(identity), so changing puzzle identity resets the component and its listeners safely.

Use Svelte 5 runes and onMount for browser APIs. Do not generate a date-dependent board during prerender. Restore state before enabling input, validate every loaded record, and do not save empty initial state over an existing save before restoring it. Reject moves after completion and corrupted or incompatible states. Keep keyboard/pointer behavior equivalent and do not hijack input fields or native navigation controls. Remove all listeners, intervals, audio, canvases, and workers on unmount.

Small JSON saves use loadSave and saveSave with puzzleKey(identity). Store a separate save-format version, the minimal resumable state, and no redundant derived board unless necessary. These localStorage APIs are synchronous: keep writes small and outside animation loops; debounce high-frequency input. Storage failure must leave a playable in-memory session and display a warning.

Validate saves against the game's resumable states, not only JSON shape. Kings deliberately permits conflicting placements and more than ten crowns: restore distinct in-bounds cells and recompute conflict feedback, rather than discarding a player's mistakes. Only a solved board may have an unrecorded completion time; validate that state against the generated regions as well as row, column, and non-touching rules. Reject corrupted or incompatible records with a truthful warning and fresh-board recovery. Generator and save-format versions are independent; an unpublished generator rename must not accidentally make incompatible old positions valid again.

Include clear instructions, accessible state descriptions, non-color-only feedback, visible focus, reduced motion, mobile-friendly controls, and an unambiguous result. Use puzzleUrl(identity, location.origin) for pinned share links. Clipboard failure needs a manual-copy alternative.

Reuse `#lib/platform/WordKeyboard.svelte` for on-page letter entry. Pass `onkey`, `disabled`, and the status element's ID as `describedBy`; Fivefold additionally passes per-letter `states` for its feedback colors and accessible descriptions. The component renders the keys only: games own entry, validation, physical keyboard handling, and dialog/editor/modifier isolation. Do not import one game's component or engine to reuse its keyboard.

Place instructions in `#lib/platform/GameHelp.svelte` within the game's existing status row, passing the game name and instruction content as children. Keep the trigger a quiet text control without a dedicated toolbar or extra vertical space. The rules appear in a labeled native dialog. Keep help available before Start/Resume and after completion; opening help must not change the board or timer policy.

Match the shared single-card layout used by Fivefold and Kings: do not add a second outline around the overall playing area. Keep board grids and region boundaries that communicate game rules.

Use `#lib/platform/ResultDialog.svelte` for completion results. Set its bound `open` state only on a fresh completion (including a Fivefold loss); restored completed puzzles show the card inline with the dialog closed. Dismissal renders the same content inline below the puzzle, and the View result button in the existing board status row moves it back into the modal. Render only one content copy to avoid duplicate headings, IDs, and controls; keep sharing state in the game so errors and manual-copy recovery survive transitions. Both presentations use the shared `.result-panel` lilac surface, plum border, rounded corners, and padding. Artwork uses ten-second CSS animation cycles with a short burst followed by a rest in either presentation; disable animation under reduced motion. Keep fresh-only board confetti separate and clear it on dismissal. Use `supportsNativeShare()` from `#lib/platform/share.js` on mount to label the result button Share or Copy. Call `shareResult({ title, text, url })` directly from its click handler to retain native user activation; provide a game/site title, spoiler-free result text without the link, and a separate pinned puzzle URL. Native sharing receives all three fields. Clipboard fallback includes the full result and URL; manual-copy recovery must do the same. Native cancellation is neutral, native failures fall back to clipboard copying, and clipboard failures need manual-copy recovery. Show a copy toast only for the `copied` outcome, not `shared` or `cancelled`. Disable the button while sharing without changing its label, and ignore asynchronous UI updates after unmount. Share buttons do not need explanatory helper sentences. Keep copy toasts with the result content so they remain in the dialog's top layer while the modal is open and stay available with the inline card.

Result dialogs use a 44px X button labeled Close result. Release the opener before `showModal()`, then focus the dialog itself with `preventScroll` so the browser neither highlights a result control automatically nor restores a stale board control on close. Keep intentional Tab navigation, native Escape, visible keyboard focus, and text editing intact.

Keep completion announcements accessible without duplicating a visible solved message above the result panel. In-play conflict and move feedback should remain visible until completion.

Pocket Games is mobile-web-first. Start the layout at 320–430px wide, including short portrait viewports, then enhance it for desktop. Primary navigation and actions need 44px-high touch targets; dense game keyboards need clear key separation and readable labels. Text inputs and copy textareas use at least 16px type to avoid iOS focus zoom. Do not require hover or landscape, block browser zoom, or hide controls beneath fixed overlays. Keep the board and controls together where practical and allow vertical scrolling on very short screens.

Keep board dimensions and playing-area spacing width-based, not dependent on viewport-height breakpoints. Mobile browser toolbars can change the viewport height while scrolling; switching board sizes or header spacing at those thresholds makes the page jump. Short screens should scroll without changing the active board's geometry.

### Interaction lifecycle lessons
- Timed games keep a start gate local to the board and render a seed-independent decorative preview until Start/Resume. A translucent layer over the actual regions still leaks the puzzle. Untimed Fivefold and Word Ladder open directly into play after restoring saves, without automatic focus movement or a gate. Do not save an empty initial state merely because a page was opened.
- Define timer policy explicitly. For gated puzzles, persist accumulated duration, start only on Start/Resume, freeze on completion, and exclude gate waiting and closed-page time. Use monotonic timing during a session rather than wall-clock deltas across reloads. Ribbon freezes and persists elapsed time on pagehide, then resets the monotonic session origin on pageshow; visibility changes alone do not pause its timer. Ribbon's Clear immediately erases the path without resetting or pausing the timer; backtracking and rewind also retain time. Preserve its historical untimed paths with null elapsed duration, including after Clear, and an explicit unrecorded-time explanation; do not manufacture past timing or silently reset saved progress.
- Native showModal() focuses a control even without autofocus, and closing restores the opener. Implement the required focus policy explicitly; do not hide keyboard focus outlines as a workaround. The shared New seed dialog leaves no control focused on open/close while preserving intentional Tab navigation and native Escape.
- With no modal control focused, key events can target the page body and bypass the dialog's own handlers. Isolate those events from game-level keyboard listeners without blocking text fields or browser default actions.
- Successful copying uses a brief, non-blocking live-region toast rather than inserting content that shifts controls. Reset its lifetime on repeated success and clean it up on unmount. Keep copy failures and selectable manual-copy text persistent; feedback must not steal focus.

## 3. Add the lazy route and catalog entry
Create src/routes/games/<id>/+page.svelte. Follow the Fivefold route's lifecycle without importing its engine. Dynamically import only your component in the browser. Resolve query parameters with resolvePuzzle(gameId, url), using the browser-local calendar date. Do not invoke generate() in a route load function or preload hook.

After successfully resolving a puzzle identity, call `rememberPuzzle(identity, location.origin)` from `#lib/platform/lastPuzzle.js`. The catalog uses this per-game selection only for the local calendar day it was opened, not the date of the selected puzzle. Bare game URLs still open today's daily, and explicit date/seed links are never overridden. Invalid puzzle links must not replace the remembered selection. Old undated navigation preferences are ignored; puzzle saves are unaffected.

Use #lib/platform/PuzzlePicker.svelte in the route header, passing gameId and the current identity (or null while resolving). Its New seed dialog owns custom-seed, date, random, and today navigation; do not duplicate per-game picker forms. Date changes stay as drafts until editing finishes or Enter confirms. Confirmation closes the dialog immediately, before navigation completes; failure reopens it with the selection preserved and an error. Keep game components and engines out of this shared component.

Keep a selected board's identity fixed across midnight. Recheck the browser-local date on focus, visibility return, and a coarse interval; offer the new daily rather than replacing an active game. Do not refresh navigation-memory timestamps merely because the date or focus changed. No daily rebuild or scheduling is needed.

Retain published generator identities to reproduce historical daily puzzles, shared links, and saved progress. Fivefold and Kings use v1. Catdog defaults to v2, requiring a complete deduction path, and retains v1's published allowance of up to 30 unresolved cells. Resolve explicit supported versions without upgrading them, and reject unsupported versions. Catdog's component must pass `identity.generatorVersion` into its generator. `unresolvedAfterDeductions(puzzle, steps?)` repeatedly propagates known relations and fills unanimous valid row/column patterns without branching or consulting the solution. Zero unresolved cells means logical completion for a valid puzzle, not a difficulty rating. Its optional `Deduction[]` collector records relation sources or the supporting line patterns; verify these steps by replaying them from the givens. New puzzles receive deterministic extra givens until this solver completes; solutions are never rerolled. Do not substitute uniqueness or a nonzero unresolved-cell cap for the no-guess guarantee. Catdog's implementation, component, route, and preview asset use `catdog`; `/games/catdog/` is canonical, while the old `/games/sunmoon/` shell redirects with the complete query and fragment. Its historical `sunmoon` puzzle identity, storage namespace, numeric pet mapping, and `sunmoon-v1` generator salt remain unchanged. Its independent `SAVE_VERSION` stays 2; versioned puzzle keys keep v1 and v2 progress separate. Kings' first-release generator and independent save-format version do not support earlier unpublished boards.

Ribbon uses generator v1 only, with a seed-derived barrier count from zero through eight; unsupported version links must show an error instead of selecting a different board. Barriers never cross the construction witness; clue pruning requires bounded exhaustive uniqueness proof. Keep wall checks in moves, completion, save validation, and every solver traversal/pruning rule, including zero- and eight-wall boards. Independent save-format v2 stores a legal path and safe nonnegative integer elapsed duration, or null for earlier unrecorded time; legal v1 saves migrate without losing their paths. The Start/Resume preview is labeled “Example layout” and uses fixed illustrative cells, unnumbered nodes, the distinct End node, and walls with the game's shared styling. Show an untouched board, without paths, visited tints, or an active-target ring; never bind it to the selected puzzle or saved path. Keep the decorative board beneath the veil, with the label and opaque Start/Resume control above it. Stop timers and flush active elapsed time on disposal; never save an untouched gate over existing progress.
Keep Ribbon's wall segments connected at shared grid vertices and board boundaries, trimming only free ends. Draw each colored stretch as one rounded centreline with an outline beneath it: inner and outer bend edges must be concentric, with constant radial thickness and tangent joins to straight runs. Do not add independently rounded corner patches or flare corners to meet an area target. Keep shared stroke constants and raster regressions for radial thickness, band bounds, ports, and interior seams in sync. Clamp short live bends to available segment lengths; wall clearance must account for the full outlined round cap. Number nodes stay wider than the ribbon with room for their state rings. The route aligns the title, New seed control, full-width description, metadata, and board in one playing column.

Ribbon's completed board must disable cell buttons without fading them, restore `touch-action: auto`, and pass pointer events through so it cannot trap page scrolling. Release active pointer capture and pending drag/rewind state on completion, Clear, pagehide, and disposal; completion during pointerdown or coalesced moves must not reacquire capture. Leaving a tap's starting cell, including moving off-board in a coalesced sample, cancels pending rewind. On release, rewind only if the pointer is still over the originally tapped cell; cancellation and lost capture never rewind. Clear acts immediately, with no confirmation or Undo button; pointer backtracking and keyboard Backspace remain available only during play.

Ribbon's canonical route and implementation live at `/games/ribbon/` and `src/lib/games/ribbon/`, with `Ribbon.svelte` dynamically imported by the route. Preserve its historical internal `thread` game ID, daily seed encoding, save/navigation keys, and `thread-v1` / `thread-v1-barriers` salts. The catalog keeps that internal ID while titles, accessibility labels, sharing, and artwork URLs use Ribbon. Convert only validated same-day saved navigation URLs from the former pathname to the canonical route; do not add an old route or source alias.



Add the route to vite.config.ts prerender entries and add a metadata-only entry in src/lib/catalog.ts. Read that entry's description for the game screen subheader so it stays in sync with the catalog card. Shared catalog code must never import your component, rules, data, worker, or engine, even through a barrel export. Keep preload options disabled unless a measured change justifies intent-based loading. Keep catalog entries compact; never embed live game instances.

Each catalog entry includes preview.src and preview.alt. Use a local 256×256 WebP under static/previews/ with a concise description of the visible board. Capture a fixed seeded sample, not a daily puzzle or the player's progress; the catalog must load only the image, never render a live game to make its thumbnail. Current captures use Fivefold seed catalog-preview with guesses CRANE, SHOUT, BLIMP, and Kings seed fixed-seed with crowns at zero-based cells 6, 14, 22, 35, 49. Catdog's existing thumbnail is a fixed decorative capture, not a claim about the current generator's seed-to-board mapping. Frame the complete board on white with a 10px inset.

Word Ladder's thumbnail at `/previews/wordladder-game-cool.webp` is a static rendering of generator-v1 seed `catalog-game-cool-579422`: destination COOL, with the initial ladder GAME → CAME → COME → CODE. The full six-step route continues CODS → COOS → COOL. It uses outlined Manrope lettering ([SIL OFL](https://github.com/sharanda/manrope)); no extra font is shipped or fetched by the application. Use a new artwork filename when changing a static preview so browser caches cannot retain the previous image at the same URL.

Word Ladder v2 separates the broad accepted-move dictionary from familiar size-35 endpoint candidates. Select endpoints inside the broad graph's largest component and compute shortest distances through all accepted words, not just endpoint candidates. Distances are informational; any legal route completes the puzzle. Pass `identity.generatorVersion` to generation and move validation, and retain the version on the puzzle for save validation. Keep v1's data, ordering, seed mapping, and shortest distances frozen; its safe ORCA leaf correction remains available. New dictionaries belong to a new generator version, not a save-format bump. Pin the upstream source and import recipe, freeze sorted data, and keep the public vocabulary notice identical to the source notice.

Ribbon's `/previews/ribbon-timed-v1.webp` is a static rendering of generator-v1 seed `catalog-preview`, showing the first ten path cells with constant-width circular bends, faint visited-cell tints matching each path segment, pastel numbered nodes, a special plum End node, and seven dark barriers. Its numbered circles use outlined geometric digits, with no additional font dependency.


Keep preview thumbnails at the right edge of catalog cards on phone and desktop layouts, vertically centered across the full card rather than just the copy row. Group category and duration together below the copy. Use compact 16px card padding and an 8px gap above the metadata without shrinking the title's 44px tap target. Reserve at least two lines for each description and keep catalog rows equal-height; unusually long descriptions must expand the cards together rather than be clipped.

Catalog card backgrounds automatically cycle through the gameCardColors array in src/routes/+page.svelte by catalog order. Do not import game code for styling or add dummy games to fill out the palette. Keep card text and focus outlines dark enough for every background.

Wrap each catalog card in one native link named by its game heading and described by its summary. The preview, metadata, and card padding must all navigate to the same game. Use a visible full-card keyboard focus outline, keep one tab stop per card, and do not nest links or buttons inside it.

The home page reads per-game destinations through `lastPuzzleHref` and falls back to each game's ordinary route when no valid selection exists for the current local day. Refresh both its displayed date and destinations on focus, visibility return, and a coarse interval; revalidate a card's destination synchronously on activation so the midnight-to-interval gap cannot reopen yesterday's selection. Preserve same-origin, matching registered-route, and pinned-identity checks; never trust an arbitrary stored URL or cross-origin navigation. Keep this shared navigation code metadata-only.

## 4. Verify the contract
- Unit-check legal/illegal moves, boundaries, completion, corrupted saves, generator invariants, and fixed seed vectors.
- Sample many seeds for validity; compare output across supported browsers/worker contexts if applicable. Quantify generation cost on a lower-powered device before claiming it is fast.
- Run npm run check, npm test, npm run build.
- Verify the actual preview process, origin, and port the user is accessing, not only a newly started server on another port. After every rebuild, stop and restart that preview, then reload browser tabs opened against the previous build. A stale preview can serve HTML whose hashed JavaScript requests return 404.
- Open the catalog first and inspect fetched resources: no game or dictionary chunks. Exercise direct game URLs, catalog-to-game navigation, and navigation between games; confirm unrelated games stay unloaded. A successful direct load does not prove client-side navigation works.
- Exercise a failed route-module request: the shared error page must offer a full-page reload preserving the complete puzzle URL and saves, plus catalog navigation. Recovery controls do not establish or fix the underlying cause.
- Actually play with keyboard and touch/click. Exercise rejected moves, win/loss, refresh with a partial draft, route changes, pinned sharing, unavailable storage/clipboard, and a narrow viewport.
- Verify clipboard success with actual copy/paste as well as missing/rejected write APIs. Clipboard read permission can be denied while writes work; readText() failure alone does not establish a sharing failure. Check toast expiry, repeated-copy timing, and persistent error recovery.
- Exercise New seed: cancel preserves the active board; empty or whitespace-only custom input stays in the modal with validation feedback. Nonblank Unicode seeds and surrounding whitespace must be preserved exactly; existing empty-seed URLs remain valid. Verify pinned dates, random puzzles, and today's browser-local daily still navigate correctly. Modal keys must not reach game handlers, including while no control is focused. Check Escape and intentional Tab navigation within the modal; opening and closing must leave no control focused. In browser automation, wait for both the closed state and the final focus state before sending follow-up keys.
- Inspect 320px, 375px, and 390px phone layouts, a short portrait viewport, and landscape. Check touch targets, text entry, browser zoom support, scroll reachability, and no horizontal overflow. Desktop interaction is additional coverage, not a substitute for phone verification.
- Exercise local midnight in multiple timezones, including non-whole-hour offsets and both DST transitions. Same-day catalog navigation must resume the selected seed/date; next-day navigation must open today's daily without deleting progress or replacing an already active board. No 24-hour date arithmetic or UTC-day shortcuts.
- Update README, any changed authoring guidance, and dictionary attribution. Use Git history for change tracking; no separate changelog is required. Do not add placeholders or nonfunctional catalog games.

### Debugging loading and navigation failures
- Start with the user's exact failing URL and navigation sequence. If multiple games fail, inspect shared client startup before changing an individual game's lifecycle or generator.
- Trace the served HTML to its startup script, route module, game component, and required styles. Inspect console exceptions and failed network requests. HTTP 200 for the document can still leave the prerendered loading shell visible when JavaScript fails.
- Reproduce a concrete failure before editing. Do not guess at `onMount`, effects, or navigation callbacks merely because loading stalls. A generic 500 is a symptom; a deliberately failed module request reproducing it does not prove that the user's original exception had the same cause.
- Keep verification levels distinct: check/tests/build, asset delivery, direct hydration, client-side navigation, and actual browser interaction each cover different failures. Passing an earlier level is not proof of a later one.
- Use available, authorized browser tooling; do not turn debugging into an unrequested browser installation. If browser execution is unavailable, a throwaway DOM/ESM diagnostic can exercise the served bootstrap, navigation, input, and failure recovery. Report that limitation explicitly: it does not verify browser compatibility or visual layout. Remove temporary diagnostics afterward.
- Distinguish diagnostic-harness failures from application failures: missing native DOM APIs or an incorrectly linked diagnostic ESM graph are not evidence of a production defect. Trace failures to the served application before changing its lifecycle or imports.
